# Generate graph

Compile semantic metadata bundles from the metadata agent into native ORION parsers.
The transformation agent generates and runs extraction code from the supplied mappings.
ORION performs graph construction, normalization, and merging. Metadata defects are reported
to the metadata team; transformation does not choose or repair semantic mappings.

## Inputs

Input: metadata bundles generated by the metadata agent. Each bundle contains
`croissant.semantic.json` or its gzip equivalent, with `semantics_plan.json`, validation
reports, and notes when supplied. `rcv:planLayout` links record sets to the plan. Entity groups,
properties, prefixes, code tables, constants, extraction paths, and dialects drive generation.
Missing, contradictory, or ambiguous semantics are recorded with source and field references
for handover to the metadata team. Supplied metadata remains unchanged.

## Generate ORION parsers

```bash
uv run python .agents/skills/transformation/generate-graph/scripts/generate_parser.py INPUT OUTPUT
```

`INPUT` can be a semantic Croissant, a source bundle, or a collection of bundles. Keep `OUTPUT`
under gitignored `data/`. For a single source, use `--infores infores:SOURCE` only for a confirmed
identity supplied outside the metadata; otherwise report the missing identity. Read
`generation_report.json`: a parser file may exist
while its source still needs an infores identity or has unsupported record sets.

The package includes one `SourceDataLoader` subclass per source, compiled mapping JSON,
source metadata, a registry, and runtime/schema snapshots shared by content hash. Incremental
generation preserves snapshots used by older parsers. Parsing versions include metadata,
runtime, and schema hashes. Regenerate after mapping, runtime, or schema changes.

## Run through ORION

Run a generated loader for a parsing-only test:

```bash
uv run --script OUTPUT/parsers/Kgbcia_SOURCE/src/parser.py PARSED --source-files FILES.json
```

`FILES.json` maps metadata file IDs to local paths or lists of FileSet member paths. Unbound
file objects are downloaded from metadata URLs. ORION's loader and KGX writer produce raw,
unnormalized `nodes.jsonl` and `edges.jsonl`; the parser writes `transform_report.json` and
record-level diagnostics. Generated scripts pin `robokop-orion==2.0.13` and require Python 3.12+.

Run native ORION ingestion, including normalization:

```bash
uv run --script OUTPUT/run_orion.py OUTPUT Kgbcia_SOURCE STORAGE --source-files FILES.json
```

The runner creates `STORAGE` and uses the Biolink version declared by the semantic plan;
a missing version is an error. ORION's disk merger combines repeated node properties during
parsing and normalization, including IDs that resolve to the same canonical node.
Normalization is lenient and gene/protein conflation is disabled by default. `--strict` and
`--conflation` change those policies; leave both off for pipeline builds (the reference says
why). Registration happens in-process, without
editing ORION's installation. See [the workflow reference](reference/orion_workflow.md).

## Outputs and boundaries

Nodes and edges follow the current flat Biolink/KGX schema. Every edge carries Biolink
provenance and `kgbcia_source_records: list[str]`, pointing to a `Mapping` and original record
key, with row number as fallback. ORION retains graph construction and merging responsibilities.

The generic reader supports explicitly described delimited tables, JSON, JSONL, compression,
archive members, code mappings, and entity/association patterns. It honors declared file null
markers and rejects ambiguous array alignment in both JSON formats. XML/RDF, databases,
specialized dialects, and joins need additional reader support when extraction rules are supplied.
Generation reports disclose these gaps; successful generation does not imply complete coverage.
Missing extraction instructions are metadata issues; unsupported readers for sufficiently
specified mappings are transformation limitations. Report these separately. A successful
partial transform with documented skips is valid. Unresolved NodeNorm identifiers are reported
outcomes, not parser failures. Filtering, augmentation, cleaning, and evaluation remain
outside this skill.

## Layout and status

* `SKILL.md`: agent instructions.
* `DESIGN.md`: compilation and ORION integration decisions.
* `reference/orion_workflow.md`: supported constructs and execution reference.
* `scripts/generate_parser.py`: one generator for all source bundles.
* `scripts/orion_runtime.py`: shared extraction using ORION's loader and writer.
* `scripts/run_orion.py`: registration and native ORION ingestion.
* `tests/`: compiler and real ORION integration tests with synthetic data.

The runtime stage CLI in `agents/transformation/cli.py` remains a stub. Generator tests run
with `make test`; native integration tests require the pinned ORION environment described
in the reference. Generated packages and source data belong under `data/`, not in git.

# Generate graph

Generate reproducible parsers for each knowledge source from metadata agent outputs,
then run those parsers through a shared graph builder to produce a Biolink graph for
the filter stage. The agent decides mappings; generated Python code performs the transform.

## Inputs

Input: metadata bundles generated by the metadata agent.
Each knowledge source provides:

* `croissant.semantic.json` or its gzip equivalent: source file locations, record sets,
  fields, entity groups, Biolink mappings, identifier prefixes, and parsing dialects.
* `semantics_plan.json`: mapping rationale, confidence, code tables, and known omissions.
* `check_report.md`, `check_report.findings.json`, and `notes.md`: validation findings,
  source limitations, and parsing issues. Use `semantics_answers.json` when supplied.

Actual source files are also required. Metadata describes those files; it does not replace
their records. Check source versions and checksums where available.

## Workflow

1. Read each metadata bundle and identify supported entities, relationships, and properties.
   Reuse existing mappings and derive additional mappings from source records and documentation
   where supported. Report ambiguous mappings and known gaps rather than inventing semantics.
   Skip layouts identifiable only by opaque references from earlier tool runs. Before generating
   a parser, check the downloaded file's actual headers and drop declared columns absent from it.
2. Generate a Python parser per knowledge source. Each parser reads the declared formats,
   compression, headers, delimiters, list separators, and extraction paths; constructs CURIEs;
   groups entity fields into candidate nodes; and creates directed relationships using explicit
   Biolink mappings and code tables. Preserve properties, evidence, and source lineage, and
   report malformed or unsupported records. Parser execution requires no LLM calls.
3. Run a common graph-building script with the generated parser files and source data
   as inputs and a per-source strict or lenient normalization setting, defaulting to lenient.
   The script executes the parsers and passes every node identifier through
   [shared/nodenorm.py](../../../../shared/nodenorm.py). Parsers declare `PARSER_API_VERSION = 1`
   and yield dictionaries from `parse(source_files, metadata)` using the
   [parser contract](reference/parser_contract.md).
4. Use canonical IDs for resolved nodes, preserving input IDs in `original_ids`. Prefer the
   source-mapped category if it is among NodeNorm's returned types; otherwise choose the most
   specific returned type using the shared rule in `DESIGN.md`. For unresolved nodes, strict
   mode excludes them and affected edges; lenient mode retains the original identifier and
   locally mapped category, recording the identifier in `original_ids`. Rewrite edge endpoints
   to the emitted IDs and report unresolved IDs.
5. Validate and serialize a `Graph` per knowledge source using
   [shared/schema.py](../../../../shared/schema.py).
   Every edge must reference emitted nodes and include `Provenance` with the source,
   file, contributing columns, and available evidence. NodeNorm supplies normalization;
   source metadata and records supply relationship meaning and provenance.

Skip conflicting or malformed records individually and report diagnostics. A source with usable
output and skipped records is a successful partial result. Only structural failures, such as
unavailable source files, an unreachable normalization service, or a parser crash, return a
nonzero builder status. The runtime CLI must propagate that status when pipeline integration
is implemented.

## Run the graph builder

```bash
uv run python .agents/skills/transformation/generate-graph/scripts/build_graph.py build.json
```

The build manifest lists parsers, metadata documents, local source files, per-source policies,
and a pinned Biolink vocabulary export. Paths resolve relative to the manifest. See the
[contract and manifest reference](reference/parser_contract.md) for the exact format and an example.
The builder writes graph JSON, a diagnostic report, and a normalization snapshot per source,
plus a build summary. Saved snapshots support offline replay.

## Outputs and boundaries

Produce reusable parser code, a schema-valid graph JSON file, and a report of mappings,
coverage, skipped records, and normalization failures. Record source versions, parser version,
model ID used for generation, and normalization details for reproducibility.

Convert all supported content. User selection, affinity cutoffs, cross-source integration,
augmentation, and conflict cleaning belong to later pipeline stages. Biolink is fixed, and
evaluation stays outside this agent. Keep source dumps and
generated graphs under gitignored `data/`; record downloads in `data/README.md`.

## Layout and status

* `README.md`: purpose, inputs, workflow, and outputs.
* `SKILL.md`: draft agent instructions.
* `DESIGN.md`: architecture, graph assembly, failure policy, and validation.
* `reference/`: parser contract and build manifest documentation.
* `scripts/`: graph builder and parser record contract.
* `tests/`: parser, graph contract, provenance, and mocked NodeNorm tests.

The graph builder and its version 1 parser contract are implemented. Automated parser generation
and pipeline CLI integration remain to be built. The runtime stage entry point remains
`agents/transformation/cli.py`. Run `make test` to include the builder's offline tests.
